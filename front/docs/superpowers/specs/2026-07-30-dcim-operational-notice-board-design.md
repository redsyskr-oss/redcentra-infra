# DCIM 운영 공지 게시판 및 레이어 팝업 설계

## 1. 목표

기존 공지사항을 단순 게시판에서 DCIM 운영 정보를 전달하는 업무용 게시판으로 확장한다.
긴급 장애·보안·출입 통제와 같이 확인 책임이 필요한 공지는 로그인 또는 대시보드 진입 시
레이어 팝업으로 노출하고 사용자별 확인 이력을 남긴다.

다음 원칙을 따른다.

- 기존 공지 본문, 첨부파일, 본문 이미지와 호환한다.
- 일반 공지는 업무를 방해하지 않고, 긴급하거나 중요한 공지만 선별해 팝업으로 노출한다.
- 공지 확인 기록은 감사 가능한 형태로 보관하되 개인정보는 최소한으로 수집한다.
- KWCAG 기준의 키보드 및 보조기술 접근성을 제공한다.
- 향후 장애·작업관리 기능과 연결할 수 있지만 이번 범위에서는 강하게 결합하지 않는다.

## 2. 공지 분류

### 공지 유형

- `EMERGENCY`: 긴급 장애
- `MAINTENANCE`: 계획 작업·점검
- `SECURITY`: 보안·출입 통제
- `GENERAL`: 일반 운영 공지

### 중요도

- `CRITICAL`: 긴급
- `IMPORTANT`: 중요
- `NORMAL`: 일반

### 운영 상태

- `SCHEDULED`: 예정
- `IN_PROGRESS`: 진행 중
- `COMPLETED`: 완료

게시기간과 실제 작업기간은 서로 다른 의미이므로 별도 필드로 관리한다.

- 게시기간: 사용자에게 공지를 노출하는 기간
- 작업기간: 장애 또는 점검이 실제로 영향을 주는 기간

## 3. 영향 범위

공지에는 선택적으로 영향 시설을 연결한다.

- 전체 시스템
- 회사
- 데이터센터
- 전산실
- 랙

초기 구현은 `scopeType`과 `scopeId`를 사용해 하나의 대표 영향 범위를 지정한다.
다수 시설 연결은 후속 확장으로 남긴다. 목록과 팝업에는 사용자가 이해할 수 있는 시설명을 표시한다.

## 4. 게시판 화면

기존 좌측 목록 구조를 DCIM 운영 게시판 형태로 개편한다.

### 상단 영역

- 전체 건수
- 새로고침
- 공지 등록
- 유형, 중요도, 상태 필터
- 제목·본문 검색

### 목록

서버 페이징을 사용하며 기본 페이지 크기는 20건이다.

표시 항목:

- 중요도 배지
- 공지 유형
- 제목
- 운영 상태
- 영향 시설
- 게시기간
- 작업기간
- 작성자
- 사용자 확인 상태

정렬 우선순위는 상단 고정, 중요도, 최신 작성일 순이다.

### 페이징

- 서버에 `page`, `size`, 필터, 검색어를 전달한다.
- 이전·다음과 현재 페이지·전체 페이지를 표시한다.
- 등록·수정 후 해당 공지가 포함된 목록을 갱신한다.
- 현재 페이지의 마지막 공지를 삭제하면 이전 페이지로 이동한다.
- 새로고침해도 현재 필터와 페이지를 유지한다.

### 상세

- 제목과 운영 배지
- 영향 시설과 게시·작업 기간
- 안전하게 정화된 HTML 본문
- 본문 이미지
- 첨부파일 다운로드
- 수정 이력 요약
- 현재 사용자의 확인 상태

## 5. 공지 등록·수정

기존 Tiptap 편집기와 첨부파일 기능을 유지한다.

추가 입력 항목:

- 공지 유형
- 중요도
- 운영 상태
- 영향 범위
- 게시기간
- 작업기간
- 팝업 노출 정책
- 확인 필요 여부

### 유효성 규칙

- 제목과 본문은 필수다.
- 종료일은 시작일보다 빠를 수 없다.
- `CRITICAL` 공지는 확인 필요가 항상 활성화된다.
- `SECURITY` 공지는 기본적으로 확인 필요다.
- 일반 공지는 강제 확인 팝업으로 설정할 수 없다.
- 완료된 작업 공지는 필요하면 게시기간까지 유지할 수 있다.

## 6. 레이어 팝업 정책

### 긴급 공지

`CRITICAL`이거나 강제 확인 대상으로 지정된 보안 공지는 다음과 같이 처리한다.

- 로그인 완료 또는 대시보드 진입 후 미확인 공지를 조회한다.
- 한 번에 여러 건이면 중요도와 게시일 순으로 한 건씩 표시한다.
- `확인했습니다`를 눌러야 닫힌다.
- ESC와 배경 클릭으로 닫히지 않는다.
- 확인 저장 성공 후 다음 공지로 이동한다.
- 저장 실패 시 재시도 안내를 제공한다.
- 서버 장애로 업무 화면이 영구 차단되지 않도록 제한된 안전 대체 경로를 제공하고 장애 로그를 남긴다.

### 중요 공지

- `확인`과 `나중에 확인`을 제공한다.
- 나중에 확인한 공지는 같은 세션에서 반복하지 않고 다음 로그인 또는 정책상 재노출 시점에 다시 표시한다.

### 일반 공지

- 레이어 팝업을 사용하지 않는다.
- 게시판과 알림 배지에서만 노출한다.

## 7. 확인 이력과 버전

공지의 의미 있는 내용이 바뀌었을 때 기존 확인 기록과 구분할 수 있도록 `version`을 둔다.

확인 기록:

- 공지 ID
- 공지 버전
- 사용자 ID
- 확인 시각

IP 주소나 사용자 에이전트는 기본 확인 기록에 저장하지 않는다. 기관 감사 정책에서 필요할 경우
기존 접속 이력 체계와 연결하며 중복 개인정보 수집을 피한다.

### 버전 증가 조건

- 제목
- 본문
- 중요도
- 공지 유형
- 영향 범위
- 작업기간
- 확인 정책

단순 오탈자 수정도 운영자가 `재확인 필요`를 선택하면 버전을 증가시킬 수 있다.
버전이 증가하면 새 버전의 확인 기록이 없으므로 사용자에게 다시 노출된다.

## 8. 데이터 모델

### Notice 확장

- `noticeType`
- `priority`
- `operationStatus`
- `scopeType`
- `scopeId`
- `workStartAt`
- `workEndAt`
- `popupPolicy`
- `ackRequired`
- `version`

### NoticeAcknowledgement

- `id`
- `noticeId`
- `noticeVersion`
- `userId`
- `acknowledgedAt`

`noticeId + noticeVersion + userId`에 유일 제약을 둬 중복 확인을 방지한다.

### 열거형

문자열 기반 열거형으로 저장해 데이터의 의미를 명확히 유지한다.
스키마 변경은 Flyway 마이그레이션으로 적용하며 기존 공지는 `GENERAL`, `NORMAL`,
게시 중 상태에 대응하는 기본값으로 이관한다.

## 9. API

### 게시판

- `GET /api/v1/notices`
  - 페이지, 크기, 유형, 중요도, 상태, 검색어
- `GET /api/v1/notices/{noticeId}`
- `POST /api/v1/notices`
- `PUT /api/v1/notices/{noticeId}`
- `DELETE /api/v1/notices/{noticeId}`

### 팝업과 확인

- `GET /api/v1/notices/pending-acknowledgements`
  - 현재 사용자에게 노출할 미확인 공지
- `POST /api/v1/notices/{noticeId}/acknowledgements`
  - 요청한 공지 버전 확인
- `GET /api/v1/notices/{noticeId}/acknowledgements`
  - 권한 있는 운영자의 확인 현황 조회

서버는 클라이언트가 전달한 사용자 ID를 신뢰하지 않고 인증 주체에서 확인자를 결정한다.
확인 요청의 버전이 현재 공지 버전과 다르면 충돌 응답을 반환하고 최신 공지를 다시 조회하게 한다.

## 10. 권한

- 공지 조회: 기관 정책상 허용된 인증 사용자
- 공지 등록·수정·삭제: 관리자 또는 공지 관리 권한
- 본인 확인 처리: 인증 사용자
- 전체 확인 현황 조회: 관리자 또는 감사 권한

역할 이름에 기능을 직접 고정하기보다 Spring Security의 권한 단위로 통제해 향후 기관별 역할 구성을 지원한다.

## 11. 접근성

- 팝업에 올바른 제목과 설명 연결
- 팝업 내부 초점 고정과 닫힌 뒤 초점 복원
- 모든 기능 키보드 조작 가능
- 색상만으로 중요도와 상태를 구분하지 않고 텍스트 배지 병행
- 상태 변경을 라이브 영역으로 안내
- 이미지 대체텍스트 필수
- 날짜와 시설명을 스크린리더가 이해할 수 있는 문장으로 제공
- 모션 감소 환경에서는 회전·전환 애니메이션 최소화

## 12. 보안과 파일 처리

- HTML은 허용 목록 기반으로 정화해 표시한다.
- 본문 이미지와 첨부파일은 Next.js 동일 출처 프록시를 사용한다.
- 저장소의 내부 주소와 자격증명을 브라우저에 노출하지 않는다.
- 파일 확장자, MIME 유형, 크기를 서버에서도 검증한다.
- 다운로드 응답에 `nosniff`와 적절한 `Content-Disposition`을 설정한다.
- 실행 파일과 허용되지 않은 형식은 업로드하지 못하게 한다.

## 13. 오류 처리

- 목록 조회 실패: 기존 목록이 있으면 유지하고 재시도 제공
- 상세 조회 실패: 상세 영역에 오류와 다시 시도 제공
- 확인 저장 실패: 팝업을 유지하고 중복 클릭을 방지
- 첨부 일부 실패: 공지는 저장하되 실패 파일명과 재시도 안내
- 오래된 버전 확인: 최신 공지로 교체해 재확인
- 빈 마지막 페이지: 자동으로 유효한 이전 페이지 조회

## 14. 테스트

### 백엔드

- 필터와 서버 페이징
- 공지 기본값과 유효성 검증
- 중요 변경 시 버전 증가
- 사용자별 확인 저장과 중복 방지
- 오래된 버전 확인 충돌
- 권한별 등록·수정·확인 현황 조회

### 프론트

- 검색·필터·페이지가 API 요청에 반영되는지
- 빈 마지막 페이지에서 이전 페이지로 이동하는지
- 중요도별 팝업 정책
- 강제 확인 팝업의 키보드·초점 동작
- 확인 성공·실패·버전 충돌 흐름
- 이미지와 첨부파일 동일 출처 다운로드

### 통합

- 로그인 후 미확인 긴급 공지 노출
- 확인 후 반복 노출되지 않음
- 중요 변경 후 재노출
- 다른 PC에서 이미지와 첨부파일 접근

## 15. 이번 구현 범위

포함:

- Notice 모델 확장과 마이그레이션
- 확인 이력과 버전 관리
- 서버 페이징·필터·검색
- DCIM 게시판 화면
- 중요도별 레이어 팝업
- 확인 현황 조회
- 기존 편집기·이미지·첨부파일 유지

제외:

- 장애 및 작업 엔티티와의 자동 양방향 연계
- 전자결재 승인선
- SMS·이메일·메신저 발송
- 다수 시설을 동시에 연결하는 복합 영향 범위

이 제외 항목들은 데이터 모델과 API를 깨지 않고 후속 단계에서 추가할 수 있다.
